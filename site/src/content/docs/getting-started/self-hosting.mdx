Everything here applies to any fork or clone. Nothing assumes a particular hosting provider — the
frontend is a static Vite build that deploys the same way to Amplify, Vercel, Netlify, or
Cloudflare Pages, and the collector is a Node script that runs the same way from the committed
GitHub Actions cron or any other scheduler.

<Aside type="tip">
This page is adapted from the repo's
[`docs/SELF_HOSTING.md`](https://github.com/SteveWang92/stackvitals/blob/main/docs/SELF_HOSTING.md).
</Aside>

## Prerequisites

- Node.js 24.18.1, as pinned in the repository's `.nvmrc`. Node 22 is no longer tested.
- Docker Desktop for the local Supabase workflow described below.

## Local development

<Aside type="caution">
Never point local `.env` at your production Supabase project. Local dev uses a separate local
Supabase stack so testing never writes into prod.
</Aside>

Install Docker Desktop, put your email in `VITE_DASHBOARD_ALLOWED_EMAIL` in `.env`, then:

```bash
npm run db:up
```

That one command starts Docker Desktop if it isn't running, boots the local Supabase stack
(applying every migration and seed), creates the login user and its allowlist row, and writes the
local URL and keys to a git-ignored `.env.local`. Companion commands:

- `npm run db:down` — stop the local stack; your data stays in its Docker volume.
- `npm run db:reset` — wipe the database, re-apply migrations and seeds, re-provision the login
  user. Use it after adding a migration.
- `npm run dev:local` — `db:up` followed by the Vite dev server.
- `npm run db:up:demo` — `db:up` plus fictional demo rows, so you develop against a full dashboard
  instead of an empty one. Also `db:reset:demo` and `db:demo`.

The login password is generated on first provision and stored as `LOCAL_DEV_PASSWORD` in
`.env.local`. Set `LOCAL_DEV_PASSWORD` (and optionally `LOCAL_DEV_EMAIL`) in `.env` to pin your
own.

## 1. Create your Supabase project

<Steps>
1. Create a Supabase project for your dashboard instance.
2. Apply migrations in `supabase/migrations/`.
3. Run `supabase/seed.sql` to create the provider registry. The collector synchronizes project
   rows from the private config in section 2 below, so production does not need hand-written project
   inserts.
4. In Supabase Auth, disable public signup if you want single-owner access.
5. Create your Auth user manually in the Supabase dashboard.
6. Add the same email to the allowlist:
   ```sql
   INSERT INTO public.dashboard_users (email, note)
   VALUES ('you@example.com', 'owner')
   ON CONFLICT (email) DO NOTHING;
   ```
</Steps>

For an existing installation, apply every migration added since the version you deployed. The
[database schema reference](/reference/database-schema/#migrations) lists the purpose of each
migration, including upgrade actions that remove retired data.

You manually create the login user in Supabase. The app checks that signed-in user's email
against `VITE_DASHBOARD_ALLOWED_EMAIL`, and the database checks the same email against
`dashboard_users` through RLS. To allow more than one person in, use a comma-separated list and
add each email to both gates.

## 2. Configure the collector

Real IDs and secrets never belong in git — put them in `.env` files or your scheduler's secret
store.

<Steps>
1. Copy `projects.example.json` to `projects.config.json` (git-ignored).
2. Replace placeholder URLs and resource IDs with your own. Any field can use `${ENV_VAR}`
   placeholders — the collector resolves them from the environment at runtime.
3. Add secrets to your local env or scheduler.
4. Run `npm test`, then `npm run collect:status`.
5. After it works locally, add the same config/secrets to your scheduled workflow.
</Steps>

Each writable collector run treats this config as the active inventory: it upserts configured
projects, deactivates omitted projects, and removes stored data for providers removed from a
project.

AWS Cost Explorer is enabled by default when AWS credentials are present. If those credentials
are intentionally limited to Amplify, Cognito, or DynamoDB reads, set
`"aws": { "costExplorerEnabled": false }` in the collector config so no Cost Explorer permission
is required.

See [Environment Variables](/reference/environment-variables/) for the full list of required and
optional secrets.

## 3. Set frontend secrets

Set these in your hosting provider's environment variables:

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_ANON_KEY`
- `VITE_DASHBOARD_ALLOWED_EMAIL`

<Aside type="danger">
Do not put `HUB_SUPABASE_SECRET_KEY`, any watched app's service-role key, AWS keys, or
Resend keys in frontend hosting env vars — only `VITE_*` variables are exposed to the browser.
</Aside>

## 4. Deploy the static site

```bash
npm run build
```

Output directory: `dist`

Any static host works — Amplify, Vercel, Netlify, Cloudflare Pages. Most hosts also offer
branch-level access control as an optional first layer; keep Supabase Auth and RLS regardless.

## 5. Add the dashboard to itself

The dashboard can track itself: add it to the collector config and set `"hubSupabase": true` so
the writable collector syncs its project row and the self-health collector targets it.

## 6. Run the scheduled collector

The committed `.github/workflows/collect.yml` runs `npm run collect:status` on a daily cron and
works as-is on any fork — just add the required secrets. Any other scheduler that can run
`npm run collect:status` works the same way.

<Aside type="note">
If your repo is public, workflow run logs are publicly visible. The collector prints project slugs,
URLs, health status, and error messages — this publishes a daily operational status feed. Keep the
collector in a private repo if that matters.
</Aside>

### Getting notified when something breaks

`collect:status` exits non-zero when the run contains a hard failure — an adapter error, a `failed`
metric, or a `failed` health check. That marks the scheduled run as failed, and GitHub emails you
about it (**Settings → Notifications → Actions**, "Send notifications for failed workflows only").
No webhook receiver and no always-on monitoring service.

Warning-level results deliberately do not fail the run: a domain three weeks from expiry would
otherwise email you daily until you fixed it. Warnings surface in the dashboard's "Needs Attention"
panel and the workflow step summary instead. Snapshots are written before the exit code is set, so a
failed run still records what it collected.

## 7. Verify

```bash
npm test
npm run lint
npm run build
```

Then open the deployed site and check:
- Signed out → login form appears
- Wrong email → sign-in is rejected
- Allowed email → dashboard renders
- Browser anon queries → RLS only returns rows for allowlisted users
